## 1. 大模型推理的基本流程

### 1.1 训练 vs 推理

| 阶段 | 特点 | 核心瓶颈 |
|------|------|----------|
| 训练 | 可以批量处理，梯度可并行 | 显存（存储参数+梯度+优化器状态） |
| 推理 | 逐 token 生成，延迟敏感 | 计算速度（每生成一个 token 都要过一遍整个模型） |

### 1.2 自回归生成的两个阶段

```
输入 Prompt → Prefill 阶段（并行处理所有输入 token）→ Decode 阶段（逐个生成 token）
```

**Prefill 阶段**：
- 处理用户输入的所有 token，计算量大但可并行
- 生成初始 KV Cache

**Decode 阶段**：
- 每次只生成一个 token，串行执行，是延迟瓶颈
- 每步都需要加载完整的模型参数

### 1.3 推理的三大挑战

1. **延迟**：用户等待时间，每多一个 token 就多一次前向传播
2. **吞吐量**：同时服务多少用户
3. **显存**：KV Cache 随序列长度线性增长

## 2. 数值格式与量化基础

### 2.1 为什么需要量化？

- 大模型参数量巨大（7B 参数 × 2 字节 = 14GB FP16）
- 推理时需要同时存储参数和 KV Cache
- 量化可以减少显存占用和计算量

### 2.2 常见数值格式

| 格式 | 位数 | 指数位 | 尾数位 | 显存占用（7B 参数） | 适用场景 |
|------|------|--------|--------|-------------------|----------|
| FP32 | 32 | 8 | 23 | 28GB | 训练（梯度） |
| FP16 | 16 | 5 | 10 | 14GB | 混合精度训练 |
| BF16 | 16 | 8 | 7 | 14GB | 训练（更稳定） |
| FP8 (E4M3) | 8 | 4 | 3 | 7GB | 推理 |
| INT8 | 8 | - | - | 7GB | 推理 |
| INT4 | 4 | - | - | 3.5GB | 推理（边缘设备） |

### 2.3 FP16 vs BF16

- **FP16**：5 位指数 + 10 位尾数，精度高但范围小（±6.55 × 10⁴）
- **BF16**：8 位指数 + 7 位尾数，范围大（±3.4 × 10³⁸）但精度稍低
- BF16 更适合训练（防止梯度溢出），FP16 更适合推理

### 2.4 量化方法分类

- **权重量化**：只量化模型权重
- **激活量化**：量化中间激活值
- **KV Cache 量化**：压缩 KV Cache 显存

## 3. 浮点数量化的本质：尾数截断 vs 指数截断

> 浮点数降精度时，"指数截断"不是"从低位或高位直接物理丢弃比特位"。

### 3.1 指数位为何不能"按位截断"？

浮点数的指数在存储时并不是一个绝对的二进制整数，而是加上了一个固定的"偏置值（Bias）"：

```
FP32：8 位指数，偏置值 = 127
  如果真实指数是 -4，底层存储：-4 + 127 = 123（二进制 01111011）

FP16：5 位指数，偏置值 = 15
```

**错误做法**：直接把 FP32 指数的低 3 位或高 3 位"物理截断"掉凑成 5 位，新二进制数减去 FP16 的偏置值 15 后，真实指数将完全偏离原本的 -4。

**正确做法**：重新计算偏置 + 极值裁切。

### 3.2 指数"截断"的真实数学逻辑

```
第一步：还原真实指数
  E_real = E_FP32_stored - 127

第二步：施加新精度的偏置
  E_FP16_stored = E_real + 15

第三步：动态范围"截断"（这才是所谓的指数截断）
  - 上溢（Overflow）：E_real 超过 FP16 上限 → 强制为 Inf 或最大值
  - 下溢（Underflow）：E_real 太小接近 0 → 强制为次正规数或 0
```

**量级对比**：
- FP32 可表示范围：约 ±3.4 × 10³⁸
- FP16 可表示范围：约 ±6.55 × 10⁴
- 超出范围的数值会被"一刀切"为边界值

### 3.3 尾数截断 vs 指数截断的本质对比

| 维度 | 操作对象 | 底层操作逻辑 | 导致的结果 |
|------|----------|--------------|------------|
| **尾数位 (Mantissa)** | 小数部分的有效数字 | **物理位截断**：直接丢弃最低的若干个比特位（例如从 23 位砍掉后 13 位，保留高 10 位） | 产生**舍入误差**。高位信息被保留，数值的绝对大小不变，但"颗粒度"变粗 |
| **指数位 (Exponent)** | 底数 2 的幂次（量级） | **逻辑极值截断**：重新计算偏置值。如果量级超出低精度支持的窗口，则直接将超出的部分"一刀切"为边界值（0 或 Inf） | 产生**范围溢出**。极值数据丢失，但处于合法范围内的数值，其量级信息被 100% 完美保留 |

**总结**：
- **尾数截断**：丢弃最低的若干比特位（精度损失）
- **指数截断**：超出低精度范围的量级被截为边界值 0 或 Inf（范围损失）
- 两者在计算机体系结构中的硬件实现路径截然不同

## 4. 量化方法详解：对称与非对称

### 4.1 核心问题

原始 FP32 范围是 [-3.4e38, 3.4e38]，如何映射到 INT8 的 [-128, 127]？

**关键洞察**：我们不需要映射整个 FP32 范围，只需要映射**实际数据的范围**。

假设一个权重矩阵的值范围是 [-10.8, 10.8]，我们要量化到 INT8。

### 4.2 对称量化（Symmetric Quantization）

```
步骤 1：找到最大绝对值 α = max(|x|) = 10.8

步骤 2：计算缩放因子 s = (2^(b-1) - 1) / α
       s = 127 / 10.8 ≈ 11.76

步骤 3：量化公式：q = round(x × s)
       例如：3.08 × 11.76 ≈ 36
       例如：-7.59 × 11.76 ≈ -89

步骤 4：反量化：x_dequant = q / s
       例如：36 / 11.76 ≈ 3.06（原始值是 3.08，有量化误差）
```

**特点**：
- 以零为中心对称映射
- 浮点数的 0 精确映射到整数的 0
- 只需要一个参数（缩放因子 s）
- 计算简单，但可能浪费量化范围

### 4.3 非对称量化（Asymmetric Quantization）

```
步骤 1：找到最小值 β 和最大值 α
       β = -7.59, α = 10.8

步骤 2：计算缩放因子 s = (q_max - q_min) / (α - β)
       s = (127 - (-128)) / (10.8 - (-7.59)) = 255 / 18.39 ≈ 13.87

步骤 3：计算零点 z = round(-s × β) + q_min
       z = round(-13.87 × (-7.59)) + (-128) ≈ 105 - 128 = -23

步骤 4：量化公式：q = round(x × s) + z
       例如：3.08 × 13.87 + (-23) ≈ 43 - 23 = 20
       例如：-7.59 × 13.87 + (-23) ≈ -105 - 23 = -128

步骤 5：反量化：x_dequant = (q - z) / s
```

**特点**：
- 不以零为中心，零点可以偏移
- 需要两个参数（缩放因子 s 和零点 z）
- 更精确地利用量化范围
- 但计算稍复杂

### 4.4 量化粒度

| 粒度 | 说明 | 精度 | 开销 |
|------|------|------|------|
| Per-Tensor | 整个张量共享一组 s 和 z | 低 | 最小 |
| Per-Channel | 每个通道独立的 s 和 z | 中 | 中等 |
| Per-Group | 每小组（如 128 个元素）独立的 s 和 z | 高 | 较大 |

### 4.5 PTQ vs QAT

```
PTQ（训练后量化）：
  训练好的模型 → 直接量化 → 推理
  优点：简单，不需要重新训练
  缺点：精度损失可能较大

QAT（量化感知训练）：
  训练时模拟量化 → 模型适应量化误差 → 训练完成后量化
  优点：精度损失小
  缺点：需要重新训练，计算成本高
```

## 5. 三值大模型 BitNet b1.58

### 5.1 核心思想

将模型权重量化为只有三个值：{-1, 0, +1}

### 5.2 为什么是 1.58 位？

- 二进制只有 2 个值（-1, +1），需要 1 位
- 三值有 3 个值（-1, 0, +1），需要 log₂(3) ≈ 1.58 位

### 5.3 量化方法（AbsMean Quantization）

```
步骤 1：计算权重的绝对平均值 α = mean(|W|)

步骤 2：归一化：W_normalized = W / α

步骤 3：四舍五入到最近的整数：W_ternary = round(W_normalized)

步骤 4：裁剪到 [-1, 1] 范围：W_ternary = clip(W_ternary, -1, 1)
```

**举例**：
```
原始权重：[0.45, -0.82, 1.23, -0.15, 0.67]
绝对平均值 α = (0.45 + 0.82 + 1.23 + 0.15 + 0.67) / 5 = 0.664

归一化：[0.678, -1.235, 1.853, -0.226, 1.009]
四舍五入：[1, -1, 2, 0, 1]
裁剪：[1, -1, 1, 0, 1]
```

### 5.4 计算优势

**传统矩阵乘法**：Y = X × W（需要乘法和加法）
```
每个元素计算：y = x₁×w₁ + x₂×w₂ + ... + xₙ×wₙ
```

**三值矩阵乘法**：Y = X × W（只有加法和减法）
```
当 w = 1 时：  y += x（加法）
当 w = -1 时：y -= x（减法）
当 w = 0 时：  y += 0（跳过）
```

### 5.5 性能对比

| 模型 | 参数量 | 显存 | 延迟 | 困惑度 |
|------|--------|------|------|--------|
| LLaMA FP16 | 3B | 7.89GB | 5.07ms | 10.04 |
| BitNet b1.58 | 3B | 2.22GB | 1.87ms | 9.91 |
| BitNet b1.58 | 3.9B | 2.38GB | 2.11ms | 9.62 |

**关键发现**：
- BitNet b1.58 在 3B 参数量时就能匹配 FP16 模型的性能
- 显存减少 3.5 倍，推理速度提升 2.7 倍
- 能耗减少 71.4 倍（7nm 芯片）

### 5.6 计算范式变革

```
传统 FP16：需要 FP16 乘法器 + FP16 加法器
三值模型：只需要 INT8 加法器（无乘法）

这意味着：
1. 硬件可以更简单、更省电
2. 可以设计专门的 1 位 LLM 加速器
3. 推理成本大幅降低
```

## 6. Tensor Parallelism（张量并行）

### 6.1 核心思想

将单个矩阵运算拆分到多个 GPU 上并行计算。

### 6.2 实现方式

```
原始矩阵乘法：Y = X × W

Tensor Parallelism（2 卡）：
GPU0: Y0 = X × W0 （W 的前半部分）
GPU1: Y1 = X × W1 （W 的后半部分）
最终结果：Y = [Y0, Y1]
```

### 6.3 优缺点

| 优点 | 缺点 |
|------|------|
| 单层计算速度提升 | 需要高带宽 GPU 互联（NVLink） |
| 通信开销相对较小 | 通信频繁，不适合跨机 |

### 6.4 典型应用

- vLLM 的 `--tensor-parallel-size` 参数
- 适合同一台机器内的多 GPU

## 7. Pipeline Parallelism（流水线并行）

### 7.1 核心思想

将模型的不同层分配到不同 GPU 上。

### 7.2 实现方式

```
GPU0: 第 0-9 层
GPU1: 第 10-19 层
GPU2: 第 20-29 层
GPU3: 第 30-39 层

输入 → GPU0 → GPU1 → GPU2 → GPU3 → 输出
```

### 7.3 优缺点

| 优点 | 缺点 |
|------|------|
| 适合跨机器部署 | 存在流水线气泡（Pipeline Bubble） |
| 通信只在层间发生，频率低 | 需要精心调度才能提高利用率 |

### 7.4 流水线调度优化

- **GPipe**：微批次（micro-batch）流水线
- **1F1B**：一个前向一个反向交替执行

## 8. KV Cache 原理与优化

### 8.1 为什么需要 KV Cache？

- 自回归生成时，每一步都需要计算注意力
- 注意力计算需要所有历史 token 的 K 和 V
- 如果不缓存，每生成一个 token 都要重新计算所有历史的 KV

### 8.2 KV Cache 的工作原理

```
生成 token t 时：
- 计算当前 token 的 Kt 和 Vt
- 将 Kt, Vt 追加到 KV Cache
- 使用完整的 KV Cache 计算注意力
```

### 8.3 显存占用

```
KV Cache 大小 = 2 × 层数 × 序列长度 × 隐藏维度 × batch_size × 字节数
```

以 32B 模型、序列长度 2048 为例：
```
总显存 ≈ 模型参数 + KV Cache + 激活值缓冲
       ≈ 64GB + 几 GB + 几百 MB
```

### 8.4 优化方法

| 方法 | 原理 | 效果 |
|------|------|------|
| **PagedAttention** | vLLM 核心创新，将 KV Cache 分页管理 | 高效内存管理，避免碎片化 |
| **KV Cache 量化** | 将 KV Cache 从 FP16 量化到 INT8/INT4 | 显存减半或更多 |
| **滑动窗口** | 限制历史长度，减少 KV Cache 大小 | 降低显存但可能丢失长程依赖 |

## 9. Flash Attention

### 9.1 核心思想

通过分块计算与累加策略，避免存储中间注意力矩阵（N × N），从而解决内存瓶颈问题。

### 9.2 数值稳定性处理

引入动态最大值（mi）调整机制，利用指数运算性质在分块计算中保持数值稳定性，确保结果与全局 Softmax 一致。

### 9.3 关键优化

让中间注意力矩阵**不写回 HBM**，全程在 SRAM 里算完，大幅减少内存访问次数。

## 10. vLLM 推理框架

### 10.1 核心特点

- **PagedAttention**：高效管理 KV Cache
- **Continuous Batching**：动态批处理
- **Tensor Parallelism**：多 GPU 并行

### 10.2 启动参数

```bash
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-1.5B-Instruct \
  --host 0.0.0.0 \
  --port 8000 \
  --max-num-seqs 1 \           # 并发请求数（类似 batch size）
  --max-model-len 1024 \       # 最大序列长度
  --attention-backend TRITON_ATTN \
  --gpu-memory-utilization 0.85 \
  --tensor-parallel-size 1     # GPU 数量
```

### 10.3 API 调用

```python
from openai import OpenAI

client = OpenAI(
    api_key="EMPTY",  # vLLM 默认不校验
    base_url="http://127.0.0.1:8000/v1",
)

response = client.chat.completions.create(
    model="Qwen/Qwen2.5-1.5B-Instruct",
    messages=[
        {"role": "user", "content": "AI 软件基础包括哪些核心内容？"}
    ],
    temperature=0.7,
)

print(response.choices[0].message.content)
```

### 10.4 多轮对话示例

```python
messages = [{"role": "system", "content": "你是一个有帮助的 AI 助手"}]

def chat_with_qwen(user_input: str):
    messages.append({"role": "user", "content": user_input})
    response = client.chat.completions.create(
        model="Qwen/Qwen2.5-1.5B-Instruct",
        messages=messages,
        temperature=0.7,
        max_tokens=512,
    )
    reply = response.choices[0].message.content
    messages.append({"role": "assistant", "content": reply})
    return reply
```

## 11. SGLang 框架与 RadixAttention

### 11.1 核心创新

**RadixAttention**：针对多轮对话（Multi-turn）和多用户并发场景，支持历史对话缓存复用。

### 11.2 适用场景

特别优化了多轮对话中的前缀共享问题，通过复用公共前缀 KV Cache 进一步节省内存。

### 11.3 vLLM vs SGLang 对比

| 框架 | 核心机制 | 适用场景 |
|------|----------|----------|
| **vLLM** | PagedAttention：KV Cache 分页管理 | 高并发、长上下文 |
| **SGLang** | RadixAttention：前缀共享缓存 | 多轮对话、多用户并发 |

## 12. 推理优化技术对比

| 技术 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| Tensor Parallelism | 矩阵拆分 | 单层加速 | 需要高带宽互联 |
| Pipeline Parallelism | 层间拆分 | 适合跨机 | 存在流水线气泡 |
| KV Cache | 缓存历史 KV | 避免重复计算 | 显存占用大 |
| 量化 | 降低精度 | 减少显存和计算 | 可能损失精度 |
| Flash Attention | 注意力计算优化 | 减少内存访问 | 需要硬件支持 |
| PagedAttention | KV Cache 分页 | 高效内存管理 | 实现复杂 |
| Continuous Batching | 动态批处理 | 提高吞吐量 | 调度复杂 |

## 13. vLLM 部署实践

### 13.1 环境配置

```bash
# 安装 vLLM
pip install -U vllm==0.22.0

# 安装相关依赖
pip install -U transformers accelerate huggingface_hub
```

### 13.2 启动服务

```bash
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-1.5B-Instruct \
  --host 0.0.0.0 \
  --port 8000 \
  --max-num-seqs 1 \
  --max-model-len 1024 \
  --attention-backend TRITON_ATTN \
  --gpu-memory-utilization 0.85 \
  --tensor-parallel-size 1 &
```

### 13.3 验证服务

```bash
# 检查端口是否监听
netstat -ant | grep 8000
```

### 13.4 常见问题

- **进程占用**：vLLM 服务启动后会一直占用终端，需要在后台运行（`&`）或使用 `nohup`
- **并发限制**：`max-num-seqs` 相当于 batch size，影响并发用户数
- **显存不足**：降低 `gpu-memory-utilization` 或减小 `max-model-len`
